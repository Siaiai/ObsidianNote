# 初始化侦察（/plan-new 用）

`/plan-new` 不是"直接规划"，而是**先读懂代码，再建索引和基线**。需求留空，后面用 `/plan-req`。

## 只读侦察清单

按顺序读，不修改任何代码：

1. **入口文档**：`README.md`、`AGENTS.md`、`CLAUDE.md`、`docs/`
2. **构建**：`CMakeLists.txt`、`Makefile`、`.uvprojx`、`.eide/eide.yml`、`package.json`、`Cargo.toml`、`pyproject.toml`
3. **测试**：`test/`、`tests/`、`*_test.*`、CI 配置
4. **入口**：`main.c` / `main.cpp` / `index.ts` / `app.py` 等
5. **关键模块**：目录结构 + 最近 `git log -20`
6. **现有机制**：错误上报、日志、配置、协议、存储、事件、定时器——找"已经存在的那一套"
7. **相关仓库**：面板/控制器/上位机这类配套仓库，各读一遍顶层结构和 README

## 输出到哪里

| 侦察结果 | 写到 |
|---|---|
| 仓库 / 分支 / 提交 / 构建 / 测试命令 | §0 基线 |
| 现有机制（位置 / 用途 / 扩展方式） | §0 机制登记 |
| 仓库表 / 关键文件 / 相关依赖 | §7 参考与索引 |
| 目录结构和模块关系 | §3 设计要点（可选 mermaid） |
| 需求 | **不写**，留给 `/plan-req` |

## 纪律

- 只读证据，不猜。路径不存在就写"未找到"，不要编。
- 多仓库时每个仓库单独一行，标清角色（面板 / 控制器 / 上位机 / 工具）。
- 侦察完先输出"我读到了什么"，等用户确认再落文档（或直接落，但必须标来源）。
- 不建框架、不写实现、不提需求。
