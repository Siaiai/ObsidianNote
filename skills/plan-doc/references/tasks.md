# 任务、变更与收尾规则

## 任务粒度

一条任务 = **一次会话能改完 + 跑完验证**。超过就拆。

拆分信号：

- 需要改 3 个以上模块或 2 个以上仓库
- 验证命令要跑 10 分钟以上
- 验收条件写成两段以上"并且"
- 需要等待外部输入（硬件、他人、真机）

拆分方式：按可独立验证的切片拆，例如「协议改完并测试」和「页面接入协议」，不要按文件拆。

## ID 规则

- 阶段前缀 + 序号：`T1-1`、`T1-2`……`T2-1`
- 只增不改；取消的号永久作废，新任务往后排
- 不要在不同文档里重复使用同一个号
- 变更号 `C1`、`C2`……同一文档内连续
- 决策号 `D1`、`D2`……同一文档内连续
- 验收项用 `V-1`、`V-2`……

## 任务优先级

| 级别 | 定义 | 处理 |
|---|---|---|
| P0 | 阻断后续任务或阻塞验收 | 立即做，一次只领一条 |
| P1 | 本轮应做，影响质量 | P0 清空后做 |
| P2 | Backlog，按影响 / 成本排期 | 记录，不阻塞 |
| P3 | 想法 / 远期 | 只记录 |

## 验收写法

必须写成 `命令 → 期望结果`：

```text
验收：ctest --test-dir build --output-on-failure → 62/62
验收：EIDE 构建 → 0 error，ROM < 128KB
验收：真机网络页改 IP 后重启 → 新 IP 生效且能读参数
```

禁止：

- 「确保正确」「功能正常」「体验良好」
- 只写「测试通过」不写命令
- 只有人工主观判断、没有可复现步骤

## 机制复用（防止多机制并行）

**一功能一机制**。同一功能只允许一条机制；并行机制是 bug。

- 任务行的 `机制：` 必填，只能写 `复用 X` 或 `新建 D#`
- 开工前先查 §0.4 机制登记；有同类机制就扩展它，不要新建
- 新建机制必须先在 §4.1 立 D 决策，写清为什么不能扩展现有
- 执行AI 发现实现会引入新机制：停下，记 D，不要顺手造
- 机制被多任务使用后，登记表“使用者”列同步更新

## 变更操作流（6 步）

```text
1. 先记 C 条目，不判断
2. 定类型：新增 / 修改 / 删除 / 延期 / 否决 / 待定
3. 扫影响四个面：
   [ ] §1 哪些未做要改 / 删
   [ ] §6 哪些已完成要重做
   [ ] §2 契约版本是否要升
   [ ] 测试 / README / AGENTS 是否要同步
4. 定处理：立即做 / 排期 / 延期 / 否决 / 待定
5. 落地：新任务写 ← C#；作废任务进 §6
6. 跑 lint
```

## 三类变化的做法

| 场景 | 做法 |
|---|---|
| 加法（不影响已完成） | 新增 C + 新任务 `T1-19 ← C1`，旧任务不动 |
| 修改（推翻已完成） | 不改旧任务；新开 `T1-20 重做 T1-4（← C1）`；§6 里 T1-4 标"被 T1-20 取代" |
| 删除 / 否决 | §1 任务移到 §6 标"取消 ← C3"，原文保留 |

**最容易做错的是"修改"**：直接编辑旧任务描述会让 AI 以为没做过，导致重做或漏掉回归。

## 状态与归档

- `[ ]` 未做或进行中
- `[x]` 验证命令已跑过且通过
- 阻塞写 `（阻塞：原因）→ 解除条件：…`
- 完成 / 取消 / 取代 / 延期全部移出 §1，进 §6
- 未确认的需求只进 §4.2（类型=待定），**不建任务**

## 会话收尾清单

每次会话结束前必须：

- [ ] §0 状态与实际一致
- [ ] §1 下一条任务明确
- [ ] §5 加一行实施记录（含验证命令与结果）
- [ ] §6 归档完成 / 取消的任务
- [ ] 顶部 `最后更新` 改为今天
- [ ] 跑一次 lint，ERROR 清零

## 执行 AI 硬约束

- 一次只做一条任务；不顺手重构无关代码
- 不 commit / push，除非用户明确要求
- 不覆盖工作区里他人的改动；开工先 `git status`
- 只写当前真实行为；未实现的标「未实现 / 建议」
- 代码片段以仓库真实代码为准，不凭文档臆测
- 结束回复固定写：改了什么、验证命令、结果、下一步建议

```markdown
- [x] **T1-1 基线** —— 记录分支与构建命令；验证：`ctest` → 20/20；结果：通过

```
