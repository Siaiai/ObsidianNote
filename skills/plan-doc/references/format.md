# 规划文档格式 v1

> 本文件是 plan-doc skill 的格式事实源。纯 Markdown，不绑定 Obsidian。
> 在 Obsidian vault 内可按 `references/obsidian.md` 补属性。
> 创建文档用 `assets/plan-template.md`；怎么用见 `sop.md`。

文档正文第一行放 `<!-- plan-doc:v1 -->`，lint 见到该标记才启用严格检查。

## 全文骨架

```markdown
---
title: {标题}
status: active
created: 2026-01-01
updated: 2026-01-01
---
<!-- plan-doc:v1 -->

# {标题}

> **一句话**：目标。
> **仓库**：`仓库A`｜`仓库B`
> **规则**：改需求先记 C；一功能一机制；执行一次只做一条。

## 0. 看板
- 阶段 / 下一条 / 本次范围 / 事实源 / 最后更新｜活跃变更｜冻结｜血缘
### 任务总览      （任务 → 状态 → 出口条件）
### 机制登记      （机制 → 位置 → 用途 → 扩展方式 → 使用者）
### 基线          （仓库 / 构建 / 测试）

## 1. 任务池
### P0（立即）      ← 一次只领一条
### P1 / P2
### 外部依赖与验收

## 2. 契约           ← 带版本，只写会影响任务的约束

## 3. 设计要点       ← 复杂任务才写

## 4. 决策与变更
### 决策（D）        ← 新建机制 / 破坏性改动
### 变更（C）        ← 需求变化，含否决

## 5. 实施记录       ← 一行一条，只写结果

## 6. 归档           ← 完成 / 取消 / 取代 / 延期

## 7. 参考           ← 源码 / 文档 / 测试入口
```

## 三个读者，各读哪里

| 读者 | 先读 | 再读 | 写入 |
|---|---|---|---|
| 人 | §0 看板 | §1 任务池 | 需求 → 发规划AI |
| 规划AI | §0 + §4 | §2、§3 | §0、§1、§4、§5、§6 |
| 执行AI | §1 单条任务 + §0 机制登记 | §2 契约 | 不写文档，只回报 |

## 0. 看板

只放"现在"：阶段、下一条、本次范围、事实源、最后更新、活跃变更、冻结、血缘。

- `下一条` 必须与任务池 P0 第一条一致
- `本次范围` 写清只做什么、不做什么
- `活跃变更` 有待定 / 待落地的 C 时写出来
- 历史一律不进看板

### 机制登记

**一功能一机制**：同一功能只允许一条机制，并行机制是 bug。

- 列：机制名 / 代码位置 / 用途 / 扩展方式 / 使用者
- 新任务开工前先查登记表；有同类机制就扩展它，不要新建
- 新建机制必须先在 §4 立 D 决策，写清为什么不能扩展现有
- 执行中发现需要新机制：停下，记 D，不要顺手造
- 机制被多任务使用后，"使用者"列同步更新

## 1. 任务池

任务行固定顺序，一条一行：

```
- [ ] **T1-5 动作** → 产出：…；验证：`命令` → 期望；机制：复用 X / 新建 D1；边界：不做什么；来源：—
```

| 字段 | 说明 |
|---|---|
| `T1-5` | 阶段号 + 序号，只增不改 |
| 动作 | 动词开头，一次会话能完成 |
| 产出 | 文件、提交、报告 |
| 验证 | `命令` → 期望结果，可复制 |
| 机制 | **必填**：复用 X 或 新建 D# |
| 边界 | 不做什么，防止范围膨胀 |
| 来源 | 普通 `—`，变更产生 `← C3` |

- P0 一次只留 1~2 条；完成立即移到 §5 + §6
- 阻塞写 `（阻塞：原因）→ 解除条件：…`
- 验收禁止「确保正确」「功能正常」这类无法复现的写法

## 2. 契约

- 标题带版本：`## 2. 契约 v2（2026-01-01）`
- 契约变更必须引用 C：`v2：新增 NETCONF_SUB 5（← C2）`
- 任务里标明所用版本：`T1-20（契约 v2）`
- 冻结后改契约必须开新阶段

## 4. 决策与变更

**决策（D）**：设计选择、新建机制、破坏性改动。一行结论。

**变更（C）**：类型只有 6 个 `新增 / 修改 / 删除 / 延期 / 否决 / 待定`。

- **否决和待定也要记**，防止 AI 重提
- 影响列写五个面：任务 / 契约 / 测试 / 文档 / **机制**
- `处理` 列写落地的任务 ID，或 `不做 + 理由`
- 已完成任务原文不改；变化一律走新任务或归档

## 5. 实施记录

一行一条，只写结果：

```
- [x] **T1-1 名称** —— 改了什么；验证：`命令` → X/X；结果：通过 / 遗留：…
- [ ] **T1-2 名称** —— 进行中：卡在…
```

没有跑验证命令不许勾 `[x]`。

## 6. 归档

结果只有 4 个：`完成 / 取消 / 取代 / 延期`。

- `关联` 列写 `← C3` 或 `→ T1-9`
- `提交` 列写短 hash 或 `—`
- 归档行原文保留，不删不改

## 图示（Mermaid，可选）

能用图表达就用图，尤其下面四类。图是辅助，**不替代任务行 / 机制登记**。

| 场景 | 类型 | 放哪 |
|---|---|---|
| 任务先后 / 依赖 | `graph LR` | §1 任务池顶部 |
| 阶段排期 / 里程碑 | `gantt` | §0 看板 |
| 机制关系 / 数据流 / 架构 | `flowchart` | §3 设计要点 |
| AI 协作 / 时序 | `sequenceDiagram` | `sop.md` 或 §3 |

```mermaid
graph LR
    T1-1 --> T1-2 --> T1-3
```

规则：

- 图只表达结构和关系，细节仍在任务行和文字里
- 复杂图放 §3 设计要点，别堆在看板
- 机制超过 5 条时，用 flowchart 画一张机制关系图
- lint 不检查 mermaid 内容，代码块整体忽略

## 血缘与冻结

- 升阶段、超 800 行或冻结时，新建 `{同名}-P2.md`
- 旧文档 `status: done`，顶部写 `> 已迁移至 新文档`，新文档写 `相关规划: 旧文档`
- 冻结写 `冻结：P1 @ commit（YYYY-MM-DD）`

## 可选：Obsidian 集成

在 Obsidian vault 内，按该 vault 的 `规范.md` 补 frontmatter（见 `obsidian.md`）。
通用字段 `title/status/created/updated` 可以保留，也可以删掉，但不要两套状态矛盾。

## 兼容旧文档

旧文档没有 `<!-- plan-doc:v1 -->` 时 lint 只报 WARN。升级步骤：

1. 补 frontmatter
2. 顶部加 `## 0. 看板`
3. 正文首行加 `<!-- plan-doc:v1 -->`
4. 跑 /plan-check，按 ERROR 修
